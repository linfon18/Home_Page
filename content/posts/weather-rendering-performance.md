这次改动的起因很直接：笔记本打开小站，风扇就开始转。页面同时运行星空、鼠标跟随、天气、Live2D 和自动终端。把效果关掉很容易，但我希望保留它们，先查清楚哪些工作没有必要重复执行。

排查期间还重做了终端边缘的雨水。早期版本像一排玻璃珠，后来改成薄水膜；下角则需要先挂住水滴，蓄大后脱落，持续积水时才形成连续细流。性能和观感在这里是同一个实现问题：应该计算水如何汇集，而不是不断增加带滤镜的元素。

## 1. 先确定比较的对象

这一轮对照的基线是本地优化前的工作版本，包含早期的圆珠水滴，并非线上历史提交。测试用 Windows 上的无头 Edge，图形后端报告为 Intel 集显的 ANGLE / Direct3D11。视口 1440 × 1000，DPR 为 2；Live2D 画布为 480 × 620，遮罩 1024，帧率上限保持 36。手机原有的 30 帧上限也没有调整。

页面加载后预热约 1.5 秒，静置、下雨和隐藏模型场景各记录约 6 秒；鼠标场景按同一条路径移动 90 次，约 7.6 秒。天气、GitHub 和一言外部请求被阻断，避免接口延迟混入测量。下雨通过本地天气设置启用。

通过 CDP 的 `Performance.getMetrics` 记录 `TaskDuration`、`ScriptDuration` 和 `RecalcStyleDuration`，另外统计 `getBoundingClientRect()` 调用次数。以下是基线与最终版本的一次完整记录，时间均为测量窗口内累计秒数：

```text
场景        窗口：前 / 后       TaskDuration：前 / 后
静置        6.003 / 6.002       0.822 / 0.877
鼠标移动    7.616 / 7.619       3.057 / 1.422
下雨        6.014 / 6.005       1.380 / 1.333
隐藏模型    6.017 / 6.007       0.324 / 0.423

鼠标移动：
样式重算累计耗时              1.681 → 0.204 秒
getBoundingClientRect 调用    4369 → 181 次
```

按窗口长度归一，鼠标移动的主线程任务占用约下降 54%，样式重算约下降 88%，布局矩形读取次数约减少 96%。下雨场景的任务耗时约下降 3%，幅度较小，不能据此认定有稳定收益。相同窗口内，Live2D 仍完成约 213～215 次渲染，没有用降低帧率换取结果。

静置和隐藏模型两组的最终记录反而更高。其他轮次也出现过波动，因此这里没有“全场景 CPU 降低”的结论。短时间的主线程记录不等于整机 CPU、GPU 功耗，更没有测到风扇转速；还需要实际笔记本上的长时间验证。新水流的完整发展周期也长于这次 6 秒的性能窗口，行为测试另外覆盖了它。

## 2. 鼠标移动为什么会拖着整页重算

原来背景视差把每帧变化的 `--scene-x`、`--scene-y` 写到根元素。即使最终只有背景需要这些值，它们仍处在整个文档的继承链上。本页的测量显示，指针移动时样式重算是明显热点。

现在保留原来的弹簧计算与移动幅度，把结果直接写到背景元素。以下是简化后的写法：

```javascript
// 只更新实际移动的元素。
wallpaper.style.transform =
  `translate3d(${x}px, ${y}px, 0) scale(1.045)`;
```

按钮磁吸也直接设置自身的 `translate`。需要吸附的元素位置会缓存；滚动、窗口变化、字体就绪、导航布局变化和 ResizeObserver 通知后才失效。一帧中先集中读几何，再集中写样式，避免在循环里反复读写交错。

旧面板高光还有一个隐藏成本：伪元素早已不显示，但 `pointermove` 仍然读取矩形并写 CSS 变量。这段监听直接删除。

文章卡片边缘的闪烁则来自交互几何本身：鼠标刚进入卡片，磁吸移动了卡片边界，鼠标又可能落到外面，反复触发进入与离开。卡片现在保持固定命中区域，颜色、箭头和内部图标继续响应鼠标，圆环也照常跟随。

背景的 3px 模糊从全屏 `backdrop-filter` 改成背景图自身的 `filter`，主题色遮罩单独保留。这里还要检查最终计算样式：较晚加载的 `experience.css` 曾覆盖前面文件的修改，导致两套滤镜叠加。修正层叠后，视差移动的是可缓存的背景层。保留的是原有模糊强度与视觉目的；像素一致性测试只针对后面的模型缓存，并不证明两个 CSS 滤镜实现逐像素相同。

## 3. Live2D 每帧究竟要重新上传什么

本站固定版本的 Cubism 渲染路径会在绘制网格时提交顶点、UV 和索引。顶点随表情、动作和物理摆动变化，必须更新；当前模型的 UV 和索引数组在这些帧之间不变。

`live2d-performance.js` 为每个网格维护独立的缓冲组。第一次正常上传，之后只省略同一缓冲中已经上传过的不可变数组。动态顶点仍按原路径提交。

```javascript
// 示意：实际实现还处理 WebGL 上下文与资源生命周期。
if (immutable.has(data) && uploaded.get(buffer) === data) {
  return;
}
glBufferData(target, data, usage);
if (immutable.has(data)) uploaded.set(buffer, data);
```

缓存的前提是“这个模型、这个运行库里的数组保持不变”，不能据此认定任何同地址的 TypedArray 都不可变。未来升级运行库或引入会修改 UV 的模型时，需要重新审计这条前提。

另一部分重复工作是相邻网格设置同样的混合、纹理单元、启用状态和着色程序。适配层记录同一 WebGL 上下文里的相关调用，只跳过已知相同的状态。Framebuffer 绑定也由绑定与删除操作维护，替代绘制时重复的 `getParameter(FRAMEBUFFER_BINDING)` 查询。

这类适配必须有明确的退出路径：释放模型时删除额外缓冲并恢复方法；上下文丢失时丢弃旧缓存，恢复后重新上传。它没有修改 vendored 库文件，但仍依赖内部渲染接口，不是通用的 WebGL 优化插件。

## 4. 缓存不能只检查“模型还在动”

性能改动容易漏掉遮罩、混合和上下文状态。回归测试先冻结同一模型帧，再分别关闭、开启缓存，渲染后用 `readPixels` 比较完整 RGBA 数组。

覆盖桌面与手机，各测试默认尺寸和 MAX，共四种组合；同帧比较的差异字节均为 0。测试同时确认画面确实有非透明像素，避免把两张空白图误判为通过。另模拟 WebGL 上下文丢失与恢复，检查恢复后的绘制和错误状态。

一次缓存统计中，已跳过上传约 6.17 MB，实际上传约 3.33 MB，跳过部分约占 65%。这是该测试窗口的缓冲上传字节比例，不是整页显存或 GPU 时间减少了 65%。

模型网格、遮罩尺寸、DPR、MAX 缩放及原帧率均保留。Pixi 的额外鼠标轮询 ticker 则关闭，因为本站已有独立命中处理。星空也保留数量和连线范围，只在距离平方已超出范围时跳过开平方。

## 5. 终端暂停时，不需要每 60ms 醒一次

旧的自动输入等待会定期检查暂停状态。鼠标停在终端里时，画面虽然没动，等待逻辑仍然不停醒来。

现在等待由状态事件唤醒。进入暂停时清除定时器，记录剩余等待时间；离开暂停后，从这个剩余时间继续。手动输入、后台、离屏和页面切换也进入同一套生命周期管理。

```text
自动输入等待
  → 悬停 / 手动接管 / 后台 / 离屏
  → 清除等待定时器，保留剩余时间
  → 状态恢复
  → 继续剩余等待
```

页面从 bfcache 返回时可以恢复；真正切走正文时，清理观察器和等待任务。这种优化对长时间停留在终端或阅读文章更有意义，不能只靠首页静置几秒的结果来评价。

## 6. 下角先挂滴，积水之后再连成流

雨水不再是一串独立 DOM 圆球。终端顶沿按约 7px 一个采样点保存湿润量，雨滴碰撞增加局部水量，相邻采样点扩散，再向左右出口排水。

每侧出口保存上游积水、流入速率、下角悬滴体积和水路是否已经湿润。少量水先形成断续水痕，沿圆角、侧边移动，途中会停滞和合流。到达底部后只增加悬滴体积，不立刻播放脱落动画。

水滴的宽度随体积的立方根增长，底部逐渐鼓起，细颈变长。达到体积阈值后，颈部短暂收缩再断开；离开边框的水滴按重力加速下落。小幅变化的阈值让两侧不会机械地同时滴落。

只有水路已经贯通、至少完成一次挂滴脱落，并且顶沿湿润量和持续流入速率都足够时，才逐渐过渡到连续细流。进入与退出使用不同阈值，避免在临界值附近反复闪动。供水不足时，细流收缩，重新变成挂滴。

```text
雨滴碰撞 → 顶沿湿润场 → 左右出口 → 沿边水痕
                                       ↓
                                下角积水、挂滴
                                       ↓
                       达到体积阈值 → 细颈断开 → 重力下落

持续供水且水路已湿润 → 连续细流 → 供水变少 → 回到挂滴
```

受控测试分别输入低速、高速和零供水，检查先蓄滴后脱落、持续供水成流、停雨后退回滴落，以及水量和活动水痕数量有界。测试没有靠等待固定秒数来触发模式；推动转换的是模拟中的供水和积水状态。

这是一套轻量的视觉近似，没有求解真实流体方程，也没有将模拟水量标定成毫升。水滴中的放大来自缓存背景图采样，不能精确折射实时正文。它们全部复用天气 Canvas，没有给每一滴水建立独立背景滤镜。

## 7. 遮挡、积雪和撑伞共用几何

终端矩形只在布局变化时重新测量。雨雪跨过顶沿时进行碰撞，绘制时把终端内部从天气层裁掉，因此屏幕里的代码保持干燥，输入也不会被效果层拦截。

雪使用另一个一维高度数组，落点增加局部厚度，表面有缓慢基础堆积，最大厚度为 12px。切换天气清理对应状态，站内切页重新绑定首页终端。

Live2D 的伞柄跟随模型手部网格，控制器把伞的几何直接交给天气层，避免天气每帧再读 DOM 矩形。雨雪在伞面被截住；选中文字的放大镜互动和生气表情优先，临时收伞。冰雹目前只触发撑伞，没有实现伞面的弹跳碰撞。

## 8. 构建与复验

网站仍然用 Node.js 14 的内置模块构建，无需给 EdgeOne 增加 Python 或浏览器依赖。下面的 Python / Playwright 只用于开发回归，和静态部署分开：

```bash
node build.js
python -m pip install playwright
python -m playwright install chromium
python tests/weather-flow.py
python tests/live2d-parity.py
```

也可以通过 `BROWSER_PATH` 指定已经安装的 Chromium 浏览器。挂滴测试不启动站点服务；模型测试临时提供 `dist/`，完成后关闭服务和浏览器。测试源码及本轮基线、最终测量记录一起保存在仓库中，后续修改可以继续对照。

天气回归另外检查手机视口、终端内部透明像素、卡片边缘命中、撑伞与放大镜切换、SPA 导航、关闭天气和系统减少动态效果。像素一致性、交互行为和主线程耗时分别回答不同问题，不能拿其中一个通过代替另外两个。

这次最明确的收益来自减少鼠标移动时的整页工作，以及重复的模型数据提交。静置功耗是否明显下降，还没有足够证据。保留这些边界，下一次排查才有可以继续使用的基线。
