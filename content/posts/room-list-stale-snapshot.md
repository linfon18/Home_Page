房间页面本来有三个人，下一次请求超时，界面一瞬间变成 0 人。网又好了，三个人再跳回来。看这次改动得从 UI 的 `Clear()` 一路追到服务获取玩家的返回值。

## 一次空结果有两种来源

请求真的成功时，`GetPlayersAsync` 会整理返回的数据，更新 `_lastKnownPlayers`。如果心跳正在恢复，或者请求出错，就拿最近一次保存的快照。服务在锁里用 `ToList()` 写入和取出，调用方可以改自己的列表结构，不会把缓存也 `Clear()` 掉。`ToList()` 复制的是元素引用，若元素对象本身还有写操作，则仍要额外考虑数据共享。

退房时清掉快照，没房间码就返回空。这个边界值得留住。如果只做一个跨房间通用缓存，刚换房发不出第一条请求时，就可能从缓存里看到上一组玩家。

## 网络恢复与重绘一前一后

界面上还有 `_isRefreshingPlayers`。一次刷新等待网络期间，第二次触发先返回。真正更新 `Players` 的部分在 Avalonia UI 线程上执行，按房主在前、加入时间在后排序。拿到空列表、界面原来有玩家且服务还连着时，也会保留现有列表。`finally` 解开标记，下次才有机会再试。

我会用下面的顺序排查闪动。先给列表三个固定玩家，用错误代替下一次响应，再给一份正常的两人列表。预期应是先保留三人，随后更新至两人。最后实际退出房间，看缓存清除后旧名字是否消失。额外留一个用例给“服务器权威返回空列表”这样的情况，防止 UI 的空值保护一直掩盖真实变化。

这段代码目前靠列表内容和连接标记推断数据是否新鲜。我以后会更愿意把 `Players`、获取时间和来源一起作为结果返回。这样“上一次看到的人”可以在恢复期间继续显示，服务端明确给空时也有独立结果可用。
